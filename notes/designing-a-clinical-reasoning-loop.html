设计一条临床推理回路Designing a Clinical Reasoning Loop

从证据检索到多专家会诊，再到结构化输出：一条可追踪的临床推理链路应该由哪些节点组成？From evidence retrieval to expert consultation and structured output: what should a traceable clinical reasoning loop contain?

Build Log 2026 年 9 月 24 日Sep 24, 2026 9 min read AttentionCoo

临床决策不是一次问答。它更像一条在时间压力下不断收敛的回路：先发现问题，再找证据，调用工具，检查冲突，最后形成可解释的行动建议。

如果只把这条链路建模成一次长 prompt，系统很容易在某个中间步骤悄然偏离，而使用者只看到最后一段流畅的文字。设计临床推理回路，首先要决定哪些状态必须显式存在。

先定义输出，而不是先写 prompt

在卒中 CDSS 里，最终输出不只有一段建议。系统还需要提供证据来源、关键临床动作、工具调用结果、专家意见和不确定性。

这些输出决定了中间状态的设计。没有显式的证据对象，就无法做引用；没有工具执行记录，就无法解释剂量或禁忌症判断；没有专家意见的边界，就无法做真正的交叉质询。

回路的五个阶段

  1. 问题结构化：把主诉、时间窗、关键生命体征和检查结果整理成可查询的临床问题。
  2. 证据检索：通过语义与关键词双路召回，把指南、文献和本地知识片段带到上下文里。
  3. 工具执行：按照评估、禁忌症、剂量等优先级调用领域工具，并记录输入和输出。
  4. 专家会诊：让不同角色的 Agent 围绕同一组证据交叉质询，而不是各自生成一份孤立结论。
  5. 证据仲裁：把证据、意见和冲突收敛成结构化结果，并通过 SSE 暴露关键过程。

为什么它不是线性 chain

真实推理需要回退：检索结果不足时要重新查询，工具输出冲突时要补充证据，专家意见不一致时要进入第二轮质询。所谓回路，意味着状态可以更新，过程可以重入，但必须有边界。

系统要为这些循环设置明确的收敛条件，例如最大轮数、证据充分性阈值和回退策略。否则，多智能体会从协作变成无休止的讨论。

工程上最容易被忽略的部分

  • 状态对象：证据、工具结果和专家意见需要稳定的数据结构，才能被 UI 和评测复用。
  • 超时与回退：任何检索或工具调用都可能失败，回退路径必须被设计，而不是临时拼出来。
  • 流式事件：SSE 不是只用于展示打字效果，它可以成为过程可观察性的基础。
  • 评测：除了最终结论，还要评测证据覆盖率、工具调用正确性和冲突处理质量。

下一步

我希望继续把这条回路做得更可验证：更细的工具级评测、更清楚的失败分类，以及更轻量的专家审阅界面。临床 AI 的进步不只来自更大的模型，也来自更诚实的系统边界。

Clinical decision-making is not a single question-and-answer exchange. It is a loop that converges under time pressure: identify the problem, retrieve evidence, call tools, inspect conflicts and produce an explainable recommendation.

If we model that loop as one long prompt, the system can quietly drift at an intermediate step while the user only sees a fluent final paragraph. Designing a clinical reasoning loop starts by deciding which states must be explicit.

Define the output before writing the prompt

In the stroke CDSS, the output is more than a recommendation. It includes evidence sources, critical clinical actions, tool results, expert opinions and uncertainty.

Those outputs determine the intermediate state. Without explicit evidence objects, citations are impossible. Without tool traces, dosing and contraindication decisions cannot be inspected. Without boundaries around expert opinions, cross-examination becomes theatre.

Five stages of the loop

  1. Structure the problem: turn symptoms, time windows, vitals and test results into a queryable clinical question.
  2. Retrieve evidence: combine semantic and keyword retrieval to bring guidelines, literature and local notes into context.
  3. Run tools: call domain tools in priority order — assessment, contraindications, dosing — and record inputs and outputs.
  4. Consult experts: have specialist agents cross-examine the same evidence instead of generating isolated conclusions.
  5. Arbitrate evidence: converge evidence, opinions and conflicts into a structured result, exposing key stages through SSE.

Why it is not a linear chain

Real reasoning needs fallbacks: retrieve again when evidence is insufficient, gather more evidence when tools conflict, and run another round when experts disagree. A loop means state can update and steps can re-enter — but it needs boundaries.

The system needs explicit convergence conditions: maximum rounds, evidence sufficiency thresholds and fallback strategies. Otherwise, multi-agent collaboration turns into an endless discussion.

The parts engineers underestimate

  • State objects: evidence, tool results and expert opinions need stable structures that the UI and evaluation can reuse.
  • Timeouts and fallback: retrieval and tools can fail; fallback paths must be designed, not improvised.
  • Streaming events: SSE is not just a typing effect. It can be the foundation for process observability.
  • Evaluation: measure evidence coverage, tool correctness and conflict handling, not only the final answer.

Next

I want to make this loop more verifiable: finer-grained tool evaluation, clearer failure categories and a lighter expert-review interface. Clinical AI improves not only with larger models, but with more honest system boundaries.
